# 05 · 变更与撤销

## 为什么单独一份文档

正向流程（进货、卖货、收款）在 02 / 03 里已经闭环，但它们全是单向的。

真实使用中最高频的逆向操作**不是退货，是录错了要改** —— 一天几十笔、3 秒一笔、全键盘，错录是必然事件而非异常。而 02 的三条设计原则恰恰让"改"变得不简单：

- 成本快照已冻结
- 库存流水只追加
- 挂账单可能已被核销

直接 `UPDATE` 或 `DELETE` 会让三张表同时失真，且事后查不出原因 —— 正是 02 开篇最警惕的"账对不上又查不出原因"。

这份文档定义唯一合法的修改路径。

---

## 核心机制：一切修改都是作废 + 重建

### 单据不可变

已提交的销售单、进货单、收款单，**任何影响金额、数量、商品、客户的字段都不允许原地 UPDATE**。

唯二允许原地改的字段：

| 字段 | 理由 |
|---|---|
| `biz_date` | 红线 2，补录必须可改。但改动会**触发核销重算**（见下） |
| `note` | 不参与任何计算 |

客户（`customer_id`）改动会改变欠款归属，走作废重建。

### 但用户看到的是"编辑"

界面上老板点「修改」，改一个数字，回车。**系统内部执行的是作废原单 + 建一张新单**，两张单通过 `revision_of_sale_id` 串成链条。

> **这个决策是有代价的。** 只允许"作废后重录"实现上简单得多（反正重录只要 3 秒）。选择支持直接编辑，是因为老板的心智就是"我改个数字"，先作废再重录会制造一个他不理解的中间状态 —— 万一他作废完被打断，这笔生意就凭空消失了。
>
> 代价记在这里：每次编辑都要重写库存流水、重算加权成本、重跑核销。**这是全系统最容易出 bug 的一段代码，必须有单测覆盖**（见 03 测试策略）。

### 数据上发生了什么

以修改一张销售单为例，单个事务内：

1. 原单标记 `voided_at = now()`，`void_reason = 'revised'`
2. 为原单每一行写一条**反向库存流水**：`type = 'void'`，`qty_base` 取符号相反的值，`unit_cost_base` **取原单行的成本快照**
3. 建新单：`rev = 原单.rev + 1`，`revision_of_sale_id = 原单.id`；原单回填 `superseded_by_sale_id`
4. 新单每一行写正向库存流水
5. 若涉及挂账客户 → 触发该客户核销重算

净效果：库存和均价回到正确值，且**每一步都在流水里留痕**。任何时候都能回答"这个商品的结存为什么是这个数"。

### 重建时成本快照怎么取

**未改动的行沿用原单的 `unit_cost_base` 快照，不重新读当前均价。**

这是红线 3 的严格推论。如果重建时统一取当前均价，老板只是把数量 2 改成 3，中间若进过一次货，这单的毛利就会莫名其妙变了 —— 他会认为软件在骗他。

| 情况 | 成本快照取值 |
|---|---|
| 行未改动 | 沿用原行 `unit_cost_base` |
| 仅数量改变 | 沿用原行 `unit_cost_base`，`cost_amount` 按新数量重算 |
| 换了商品 / 新增行 | 取**当前** `inventory.avg_cost_base` |

### 报表口径

所有报表、看板、毛利统计、库存汇总**一律过滤 `voided_at IS NULL`**。

作废单不参与任何汇总，只在单据详情页和库存流水回溯里可见。

## 退货 ≠ 作废

两件事，不要混：

| | 作废 | 退货 |
|---|---|---|
| 含义 | 这笔生意**没发生过**（录错了） | 这笔生意发生了，**后来退了** |
| 业务日期 | 无，原单从历史中消失 | **退货当天**，不是原单日期 |
| 报表 | 原单不参与任何汇总 | 原单保留，退货冲减退货当日 |
| 典型场景 | 单价打错、数量多按一个 0、选错商品 | 客人买错、质量问题、宴席剩余退回 |

把退货当作废处理，会让"上个月营业额"凭空缩水 —— 那笔生意确实做过。

一期实现 `sales:return`，支持整单退和按行部分退。

**退货入库的成本必须取原单快照，不能取当前均价。** 否则中间进过一次货、均价变了，退一笔货就会凭空产生毛利或亏损。

退货产生：

- 一张 `sales` 记录，`total_amount` 为负，`return_of_sale_id` 指向原单，`biz_date` 为退货当天
- 库存流水 `type = 'return'`，`qty_base` 为正（货回来了），`unit_cost_base` 取原单快照
- 若原单是挂账 → 客户欠款相应减少，触发核销重算（可能因此产生预收）

## 核销是派生结果，不是历史记录

### 结论

`payment_allocations` **不是流水，是缓存**。它可以被随时整体删除，并从 `sales` + `payments` 完整重算，结果唯一确定。

### 为什么必须这样

这不是为了优雅，是被两条已有规则逼出来的：

> 红线 2：业务日期可改，补录是常态
> 核销规则：按 `biz_date` 升序 FIFO

老板补录一张上个月的挂账单，它就该排进 FIFO 队列更靠前的位置。但已经写好的 allocations 是按旧顺序算的，**不会自己更新**。

后果不是小数点误差，是**账龄错了** —— 而"最早一笔 45 天前"正是收款页的排序依据，也是老板决定先给谁打电话的依据。一个按错误账龄排序的催收列表，比没有列表更糟。

一旦接受"allocations 可重算"，撤销、补录、改期、退货四个问题**一次性消失**。

### 重算算法

作用域是**单个客户**，不是全库。

```
rebuildAllocations(customer_id):
  1. 删除该客户全部 payment_allocations
  2. 取该客户所有未作废的挂账销售单（含退货负单），
     按 (biz_date, id) 升序 → sales[]
  3. 取该客户所有未作废的收款，
     按 (biz_date, id) 升序 → payments[]
  4. 双游标推进：每笔收款去填最早的未结清单，
     填满该单则推进到下一张
  5. 收款用尽即止，剩余单据保持未结清
  6. 所有单填满后仍有剩余收款
     → 记为该客户的预收余额，不写 allocation
```

排序键带 `id` 是为了消除同日多单的歧义 —— 否则重算结果不稳定，单测会随机失败。

单店数据量下这是毫秒级操作，**不需要增量优化**。

**幂等**：同样输入反复执行结果一致。这是可以写单测的，也应该写。

### 触发时机

| 事件 | 重算范围 |
|---|---|
| 新增挂账销售单（含部分付） | 该客户 |
| 作废 / 修改挂账单 | 该客户；若改了客户则**两个客户都算** |
| 修改挂账单的 `biz_date` | 该客户 |
| 销售退货 | 该客户 |
| 新增 / 作废 / 修改收款 | 该客户 |
| 后台手工触发 | 指定客户或全部客户 |

最后一条是逃生舱：万一 allocations 因 bug 失准，**重算一次即可自愈**，不需要人工去改数据。这是把它做成派生表的额外收益。

## 预收余额

超额收款照收不误，分配不完的部分自动成为预收。

```
客户净欠款 = SUM(未作废挂账单.total_amount) − SUM(该客户未作废收款.amount)
```

- 结果 > 0 → 欠款
- 结果 < 0 → **预收**，界面显示「预收 ¥300」
- 下次挂账买货时，重算自动把这 300 核销掉，无需任何额外操作

**不需要新表、不需要新字段。** 它是"allocations 可重算"的免费副产品：收款分配不完的余额就是预收。

界面上：收款页客户列表里预收客户排在最后，灰色显示，**不混进催收队列** —— 催收列表只放真欠钱的人。

## 部分付（卖货时先收一部分）

老王拿走 1000 的货，当场给 300，剩 700 挂账。

### 数据表达

部分付**不是第三种结算方式**，它就是一张挂账单 + 一笔同日收款：

1. 建销售单：`settle_type = 'credit'`，`customer_id` 必填
2. 同一事务内建一条 `payments` 记录：金额 300，`biz_date` 同单，`method` 为选中的收款方式
3. 触发该客户核销重算 → 这 300 自动核销到这张单上

好处是不引入新状态：欠款、账龄、核销、预收全部沿用既有逻辑，一行特殊代码都不用写。

### 对红线 4 的影响

红线 4 是「结账不弹对话框」。部分付**必然**要多两个输入（客户 + 已收金额），这和红线冲突。

约束：**部分付只能是第三条路径，绝不能污染前两条。**

- `F8` 现金收讫：一键完成，不变
- `F9` 挂账：只选客户，不变
- `F7` 部分付：选客户 + 输金额 —— 新增，且只有按了 F7 才会出现输入框

九成单子走 F8，红线 4 保住了。

## 进货单的作废与修改

比销售单麻烦，因为**加权成本是有序累积的**。

作废一张中间的进货单，严格来说此后所有销售单的成本快照都应该重算。但这违反红线 3（历史毛利不可变动），且会让老板上个月已经看过的利润数字发生变化。

**取舍：作废进货单只调整当前库存和均价，不回溯修改任何历史成本快照。**

反向调整公式：

```
new_qty = old_qty − void_qty

if new_qty <= 0:
    new_avg = old_avg           # 无从推算，保持不变
else:
    new_avg = (old_qty * old_avg − void_qty * void_cost) / new_qty
    if new_avg < 0:
        new_avg = 0             # clamp，并写一条告警
```

**`new_avg < 0` 是真实可能发生的**：若作废的是一笔高价进货，而此后又进了大量低价货把均价拉低，反算就会得到负数。必须 clamp 到 0 并告警 —— 否则后续所有毛利全错，且无人察觉。

这个偏差可以接受，因为下次正常进货时加权公式会把均价拉回合理区间，且烟酒进价波动本就不大。

但**界面必须写明**：「作废进货单不会修改已售出商品的历史成本」。不说清楚，老板会以为作废能把账"完全恢复原状"。

## 收款单的作废与修改

三者里最简单：收款没有成本快照，也不动库存。

- **作废**：标记 `voided_at` → 重算该客户核销
- **修改金额 / 日期 / 客户**：作废 + 重建 → 重算（改客户则两个客户都算）

## 抹零与整单折扣

「合计 1330，抹个零给 1300」在烟酒店是日常，团购大单必然带折扣。

**不允许用改单价来凑。** 单价被改脏之后，"中华卖多少钱"这个问题就再也查不准了，而单品利润排行、建议售价全都依赖它。

`sales` 增加 `discount_amount`：

```
original_amount = SUM(sale_items.amount)              # 折前合计
discount_amount = 抹零 / 折扣金额，默认 0
total_amount    = original_amount − discount_amount   # 应收，存库
gross_profit    = total_amount − cost_amount          # 折扣自然吃进毛利
```

折扣**计入毛利、不摊到行**，符合老板心智（"这单让了 30 块"），也避免了摊分产生的小数误差。

界面：卖货页合计行右侧一个小输入框，直接输折后金额，系统反算 `discount_amount`。

## 对里程碑的影响

这份文档的内容落在两处：

- **M1** 建表时就要带上 `voided_at` / `rev` / `discount_amount` 等字段。等 M2 再加就是一次迁移
- **M2.5** 新增一个里程碑，专做逆向 action，依赖 M2 的正向 action 完成

验收标准新增一条：

| 场景 | 目标 |
|---|---|
| 改一笔录错的单（改数量后回车） | ≤ 10 秒，且库存、均价、欠款三处同步正确 |
