# 03 · 技术架构

## 选型决策记录

### 后端：Fastify + SQLite（原选 NocoBase，M0 实测后推翻）

**当前结论：不用 NocoBase，自己写一层薄后端。**

原方案是拿 NocoBase 当 headless 后端，买它的五样东西。M0 把环境真正跑起来之后，这笔账重算了一遍：

| 当初买的 | 估值 | M0 后的实际情况 |
|---|---|---|
| 后台管理界面 | **很高**（"自己开发至少两周"） | **归零**。NocoBase 不发预构建的后台前端，要它就得装回整套前端构建链、在便携包里多塞几十 MB。权衡后决定不要后台 |
| 数据建模 → 自动 CRUD API | 高 | **打折**。11 张表里只有商品 / 客户 / 供应商这 3 张用得上通用 CRUD，其余全是自己写的事务 action |
| 用户认证 / Token | 中 | **归零**。无密码自动登录、单人使用，ACL 是纯负担 |
| 工作流引擎 | 中 | 二期的推测性需求 |
| 数据库迁移管理 | 中 | 还在，但任何迁移工具都能做，几十行就够 |

五项里两项归零、一项打折，剩下"3 张表的 CRUD + 迁移管理"。

而代价是实打实的：

- **1594 个依赖包**，装进一个要拷给店主的便携包
- M0 一天踩了三个坑，全出在它自己的包管理上（见下方「M0 踩坑存档」）
- 将来要在店主的电脑上升级这 1594 个包
- 前端会耦合到它的 `:list` / filter DSL

**还有一条更硬的理由**：`docs/02` 里那段"SQLite 没有原生 DECIMAL，必须守两条舍入纪律"，是被 Sequelize 逼出来的妥协。自己写数据层就能**用 INTEGER 存分**，这一整类舍入问题根本不存在 —— 不需要纪律，因为没有浮点。台账系统里这比什么都重要。

新方案：

| | |
|---|---|
| HTTP | Fastify |
| 数据库 | **better-sqlite3**（同步 API，单机单人比异步驱动简单得多） |
| 迁移 | `migrations/*.sql` + 几十行的 runner，每个迁移一个事务 |
| 校验 | Zod |
| 金额 | **INTEGER 分**；单位成本 INTEGER 万分之一元 |

实测依赖从 1594 降到 **61**，安装从 4 分钟降到 **10 秒**。

> 换来的成本：商品 / 客户 / 供应商的增删改查要自己写。但我们的查询就那么几个（拼音搜商品、按日期列流水、单品毛利排行），手写 SQL 比学它的 filter DSL 更省事也更好调。

> **NocoBase 版本的 M0 完整保留在 git 历史里**（提交 `562751d`）。若将来结论反转，那条路是通的、跑起来过的。

### M0 踩坑存档（NocoBase 相关，留作决策依据）

即使不再用它，这三条也值得留着 —— 它们是推翻选型的证据，也是评估同类框架时的检查项：

**1. pnpm 装不了 NocoBase。** 它发布的 registry 元数据里 `deprecated` 字段是数组，而规范要求字符串。pnpm v12 解析严格，直接丢弃整个版本条目，于是它一边报"找不到 2.2.15"一边提示"最新版就是 2.2.15"。1132 个已发布版本里 **831 个**中招，清缓存和 `--force` 都无效。

**2. 官方脚手架不给 SQLite。** `create-nocobase-app -d` 只接受 postgres / mysql / mariadb / kingbase，但运行时 `SqliteDialect` 与它们并列注册着，是一等方言 —— 只是没暴露。

**3. `preset-nocobase` 会让大半个后台静默失效。** `plugin-block-list@2.2.15` 把 `@nocobase/client` 声明成 `1.x`，同版本其余六十多个插件都声明 `2.x`。npm 为满足这一个包，把 **76 个包整体下沉**进 preset 自己的 `node_modules`，而 NocoBase 按顶层 `NODE_MODULES_PATH` 找插件 —— `plugin-client` / `ui-layout` / `flow-engine` 全部"查无此包"，**跳过时一声不响**。60 个插件只活了 30 个。

第 3 条最值得记：**一个写错的依赖声明，废掉了大半个产品，而且不报错。**


### 前端：独立 Vite 工程

前端 100% 自研，UI 完全可控，包体积小。

> 原来这里列了四个方案 A/B/C/D 做对比，三个都是围绕"怎么跟 NocoBase 的前端体系共处"。后端换掉之后这个对比没有意义了 —— 现在只有一种方案：前端是独立工程，后端是给它服务的 HTTP API，两边都是我们自己的。


### 数据库：SQLite

本地单机单人，PostgreSQL 是过度配置：

- 零配置，不用单独跑数据库进程
- **整个数据库就是一个文件**，备份 = 复制文件，恢复 = 覆盖回去
- 单人读写性能绰绰有余

> **已核实（2.2.15）**：SQLite 仍是一等方言。`@nocobase/database` 的 `registerDialects()` 把 `SqliteDialect` 与 mysql / mariadb / postgres 并列注册，`options.storage` 也有完整的路径处理逻辑。
>
> **但官方脚手架不给这条路**：`create-nocobase-app` 的 `-d` 只接受 postgres / mysql / mariadb / kingbase，模板依赖里也只有 `mysql2` / `mariadb` / `pg`，sqlite 只出现在它的测试环境模板里。
>
> 因此本项目**不使用官方脚手架**，自己在 pnpm workspace 里建等价的 server 包，手工配 `DB_DIALECT=sqlite` + `DB_STORAGE`，并自行安装 `sqlite3` 驱动（sequelize 6 用的是 `sqlite3`，不是 `better-sqlite3`）。
>
> 若将来 2.x 真的移除 SQLite，退回单机 PostgreSQL，备份改用 `pg_dump`。

### 包管理器：npm

用 npm workspaces。依赖只有 61 个包，pnpm 的磁盘优势在这个量级上没有意义，不值得多引入一个工具。

> 历史原因：NocoBase 时期是**被迫**用 npm 的（pnpm 解析不了它的元数据，见「M0 踩坑存档」）。现在换不换都行，保持现状。


### 原生模块：better-sqlite3

用 `better-sqlite3` 而不是 `sqlite3`：**同步 API**。

单机单人、一天几十笔，异步驱动带来的只有回调和 Promise 的噪音，没有任何吞吐收益。而事务型 action（一笔销售要连着改四张表）用同步 API 写出来是直白的顺序代码，不用担心 await 之间漏掉事务边界 —— 这类错误恰恰是最难查的。

连接上固定三个 pragma：

```
journal_mode = WAL      读写不互相阻塞，崩溃后不易损坏
foreign_keys = ON       SQLite 默认是关的，不开外键约束形同虚设
synchronous = FULL      断电安全优先于写入速度 —— 这是台账不是缓存
```

**已核实**：Node 24 / Windows x64 有预编译二进制，不需要 Visual Studio 构建工具。实测 SQLite 引擎 3.53.4。


## 技术栈

**后端**
- Fastify
- better-sqlite3（SQLite 单文件）
- Zod 做入参校验
- 迁移：`src/db/migrations/*.sql` + 自写 runner

**前端**
- Vite + React 18 + TypeScript
- Tailwind CSS（**不用组件库**）
- TanStack Query（数据获取、缓存、失败重试）
- React Router

**字体**
- 思源黑体 Noto Sans SC + IBM Plex Mono，随包发布不走 CDN（见下）

不用 Vant / Antd Mobile 之类组件库的原因：本项目要求字号和点击区域比常规大一号（使用者四五十岁），套组件库还得逐个覆盖样式，不如直接手写一套尺寸规范。


## API 设计

### 基础 CRUD（自己写）

只有三张表需要通用增删改查，各自就那么几个路由：

```
GET    /api/products          列表 / 搜索（拼音三路匹配）
POST   /api/products          新建（含卖货页就地建）
PATCH  /api/products/:id      改价、改单位换算
GET    /api/customers         列表 / 搜索
POST   /api/customers
GET    /api/suppliers
POST   /api/suppliers
```

其余的表**一律不暴露通用写接口** —— 销售单、进货单、库存流水只能通过下面的事务 action 产生。直接开一个 `POST /api/sales` 出去，等于把"库存流水是唯一真相来源"这条原则交给调用方自觉。


### 业务 action

**这是后端的主体。** 每个 action 在**一个数据库事务**内完成全部副作用，前端一次请求搞定一件事。

better-sqlite3 的同步 API 让这件事很直白：`db.transaction(() => { ... })()`，中间任何一步抛异常都整体回滚，不需要担心 await 之间的事务边界。


| 接口 | 事务内做的事 |
|---|---|
| `POST /api/sales/checkout` | 建销售单 → 建明细 → 读取当前 `avg_cost_base` 冻结为成本快照 → 应用抹零算出 `total_amount` → 扣 `inventory.qty_base` → 写 `stock_movements` → **部分付时同时建一条 `payments` 并重跑该客户核销** |
| `POST /api/purchases/receive` | 建进货单 → 建明细 → 按移动加权公式更新 `inventory.avg_cost_base` 和 `qty_base` → 写 `stock_movements` |
| `POST /api/payments/collect` | 建收款记录 → **全量重跑该客户核销**（不是增量追加）→ 写 `payment_allocations`，分配不完的余额成为预收 |
| `GET /api/reports/dashboard` | 今日营业额、今日毛利、本月毛利、欠款汇总、异常提醒 |
| `GET /api/reports/profit` | 日/月毛利趋势、单品利润排行、滞销预警 |
| `GET /api/customers/debts` | 欠款客户列表，含净欠款与账龄，按账龄倒序。预收客户单独列在末尾 |
| `POST /api/backup/now` | 立即备份数据库文件 |
| `GET /api/seed/brands` | 列出预置目录中的品牌，供首次启用时勾选 |
| `POST /api/seed/import` | 按勾选的品牌导入商品骨架，价格留空。**跳过已存在的同名商品**，可重复调用 |
| `GET /api/onboarding` | 启用向导四步的完成情况。**现算，不落库** —— 见 docs/07 |
| `POST /api/onboarding/dismiss` | 关掉/重开看板上的上手清单 |
| `POST /api/onboarding/skip-stock` | 期初库存那步选了跳过 |
| `POST /api/onboarding/opening-stock` | 期初库存。落成一张 `note = '期初库存'` 的**普通进货单**，无特殊规则 |

### 导入导出（M1.5 / M6）

| 接口 | 做的事 |
|---|---|
| `POST /api/products/parse-import` | 解析清单文本或 xlsx，返回**预览**，不落库。逐行返回解析结果与失败原因 |
| `POST /api/products/import` | 按预览结果落库。**同名跳过**，幂等，可反复导 |
| `GET /api/products/export` | 全部商品与价格导出 xlsx。**这份同时就是导入模板** |
| `GET /api/reports/export` | 本月明细：每一笔销售 + 成本快照 + 毛利 |
| `GET /api/customers/export-debts` | 欠款表：客户、净欠款、账龄、最早一笔 |

**清单解析规则**，只有两种写法，用 `-` 分隔：

```
名称 - 单位                 →  base_unit = 单位
中华(硬) - 单包                base_unit=包

名称 - 大单位 - N小单位      →  base_unit=小单位, pack_unit=大单位, pack_ratio=N
中华(硬) - 条 - 10包           base_unit=包, pack_unit=条, pack_ratio=10
```

- 拼音自动生成，价格一律留空（各店不同，导完在商品页批量填）
- **同名即同商品**，跳过不新建（理由见 [02 的 products 表](02-数据模型.md#products-商品)）
- **单行解析失败不影响整批**。失败行标红返回，允许在预览表里就地改完再导 —— 整批失败是这类功能最常见的弃用原因

导出用 `exceljs` 直接写流，不落临时文件。一期不做导出范围/字段配置，一个按钮下一份固定结构的表。

### 逆向 action（M2.5）

设计依据见 [05-变更与撤销](05-变更与撤销.md)。这批接口的实现复杂度**高于正向接口**，它们是全系统最需要单测的部分。

| 接口 | 事务内做的事 |
|---|---|
| `POST /api/sales/void` | 标记 `voided_at` → 按**原单成本快照**写反向库存流水（`type='void'`）→ 回滚 `inventory` → 挂账单则重跑该客户核销 |
| `POST /api/sales/revise` | 内部 = `void` 原单 + `checkout` 新单，串 `revision_of_sale_id`。**未改动行沿用原成本快照**，新增行取当前均价 |
| `POST /api/sales/return` | 建金额为负的退货单，`biz_date` 为**退货当天** → 按原单快照入库 → 挂账单则重跑核销 |
| `POST /api/purchases/void` | 反向调整 `inventory.qty_base` 与 `avg_cost_base`，均价反算为负时 clamp 到 0 并告警。**不回溯历史成本快照** |
| `POST /api/purchases/revise` | = `void` + `receive` |
| `POST /api/payments/void` | 标记 `voided_at` → 重跑该客户核销 |
| `POST /api/payments/revise` | = `void` + `collect`；改客户则**两个客户都要重跑** |
| `POST /api/allocations/rebuild` | 维护用逃生舱。指定客户或全部客户，重算核销。幂等 |

最后一个接口是这套设计的安全网：**allocations 万一失准，重算一次即自愈**，不需要人工改数据。

### 为什么业务逻辑不能放前端

若前端直接调通用 CRUD 来"卖一笔货"，需连发四个请求：建单 → 建明细 → 扣库存 → 写流水。中间任何一步失败，数据就脏了且无法自愈。必须服务端事务包裹。

### 没有后台管理界面

**已决策：不做。**

NocoBase 那个"免费的后台"是选它的主要理由，而它并不免费（要装回整套前端构建链现编）。权衡后连同 NocoBase 一起放弃了。

后台原本的三个用途，各自有替代：

| 用途 | 替代 |
|---|---|
| 改错账 | 已经是产品功能（改单 / 退货走 action），本来就不该直接改库 —— 见 [05](05-变更与撤销.md) |
| 导出 | 一期要做的 Excel 导出 |
| 查底层数据 | 任意 SQLite 客户端直接打开 `data/ledger.db` |

第一条尤其重要：**"能直接改库"从来不是优点。** 绕过 action 改数据，会让库存流水、成本快照、核销三者失去一致性，而且事后查不出是谁改的。


## 认证：无密码自动登录

服务只监听 `127.0.0.1`，能打开页面的人已经坐在柜台电脑前了。**密码挡不住任何人，只会挡住老板自己。**

- 服务首次启动时创建一个固定的内置用户
- 前端启动时用内置凭证静默换取 token，**token 不设过期**
- 不做登录页，不做登出按钮

真正的理由不是省事，是**消除一类故障**：token 过期那天老板会看到白屏或 401，他不会读错误信息，只会认为"软件坏了"，然后打电话给你 —— 或者回去用本子。一个每天都要用的本地工具，不该有任何一天会因为会话问题打不开。

没有后台，也就没有第二套登录。要查底层数据就用 SQLite 客户端直接开 `data/ledger.db`。

> 安全边界记在这里：这个设计假设**柜台电脑是可信的**。若将来要让服务监听局域网（比如老板想在仓库用平板看库存），必须同时补回认证 —— 那时它才真正挡得住人。

## 字体与离线资源

**柜台电脑可能没有稳定网络，所有字体必须随包发布，绝不留 CDN 引用。** 断网那天如果字体掉回默认，金额列会参差不齐 —— 而金额对齐正是这套界面可读性的地基。

| 用途 | 字体 | 许可 |
|---|---|---|
| 中文正文 | **思源黑体 Noto Sans SC** | SIL OFL 1.1，可随软件自由分发 |
| 数字与金额 | **IBM Plex Mono** | SIL OFL 1.1 |

### 为什么不是苹方

苹方（PingFang SC）是苹果随 macOS / iOS 授权的系统字体，**不允许随第三方软件分发**，而且 Windows 机器上根本没有这个文件。思源黑体是气质最接近的可分发替代。

（若要更接近苹方的圆润观感，HarmonyOS Sans SC 也可用，授权是"免费商用"但条款不如 OFL 干净。只给一两家店自用可以接受。）

### 打包纪律

- **子集化到 GB2312 字集**（6763 字）。全字集 3 万字会让便携包白白大出十几 MB
- 单字重 woff2 约 2–3MB，只打 Regular 和 Medium 两个字重，合计约 5MB
- `@font-face` 指向包内相对路径，兜底栈 `'Noto Sans SC','PingFang SC','Microsoft YaHei',sans-serif`
- 金额数字一律 `font-variant-numeric: tabular-nums`

## 部署：Windows 免安装便携包

柜台电脑是 Windows 家用机，老板自己用。**不上 Docker**（太重、要 WSL2、吃内存）。

### 发布物结构

```
烟酒台账/
├─ 安装.bat            首次运行一次：注册服务 + 建桌面图标
├─ 卸载.bat
├─ runtime/node/       便携版 Node.js，免安装
├─ app/                后端（Fastify + 迁移文件）
├─ web/                前端静态文件
├─ data/
│  └─ ledger.db        ← 全部数据就这一个文件
├─ backup/             自动备份
└─ 后台启动.vbs        无窗口启动（不用第三方服务管理器）
```

整个目录可整体复制。**换电脑、重装系统只需拷贝这个文件夹。**

实测 **8.9 MB**（不含便携版 Node）：后端 bundle 3.2MB、better-sqlite3 2.0MB（它自带 8 个平台的预编译二进制，包里只留 win32-x64）、前端 3.9MB（其中字体 3.4MB）。

**所有相对路径按应用根目录解析，不按 `process.cwd()`** —— cwd 取决于谁怎么启动的，双击 `.bat` 和从任务计划里拉起就不是同一个值。这条踩到过：不 cd 进包目录启动，数据库会建到别处去。

### 后台运行

**没有用 nssm**，改用 Windows 自带的能力 —— 便携包里多一个来历不明的 exe，在店主的电脑上是个说不清的东西。

| 要的 | 怎么做的 |
|---|---|
| 无黑窗口 | `后台启动.vbs` 用 `WScript.Shell.Run(..., 0, False)` 隐藏启动。实测进程 `MainWindowTitle` 为空 |
| 开机自启 | `安装.bat` 里 `schtasks /sc onlogon` 注册任务计划；没权限也只提示一句，不挡手动启动 |
| 崩溃自动重启 | **还没做。** 这是相对 nssm 唯一真正缺的一块 |

老板不会去分辨哪个黑窗口能关、哪个不能关 —— 一旦误关，柜台上正在录的那笔单就没了。所以隐藏窗口不是美观问题。

> 要补崩溃重启，任务计划本身支持"失败后重启"，或者加个几十行的 watchdog。
> 但补之前得先知道它会不会崩 —— 现在还没有真实使用数据。

### 桌面入口

创建快捷方式，目标为：

```
msedge.exe --app=http://localhost:13000
```

`--app` 模式无地址栏、无标签页、独立任务栏图标，看起来就是个本地桌面软件，而不是"打开浏览器输网址"。Edge 在 Win10/11 上必定存在，不需要假设装了 Chrome。

端口选 `13000` 一类不常用端口，避开冲突。仅监听 `127.0.0.1`，不对外暴露。

### 前后端同域

前端构建产物由 Fastify 用 `@fastify/static` 一并托管：`/` 出前端，`/api` 走后端。省掉 CORS 和跨域问题，也省掉第二个进程。

## 备份与恢复

> **本地部署的头号风险不是技术问题，是数据丢失。**
> 跑在云上硬盘坏了还有服务商快照；跑在柜台电脑上，硬盘坏了就是几年台账全没，而老板绝不会自己备份。
> 因此备份不是运维事项，是**一期必须交付的产品功能**，优先级高于利润报表。

### 自动备份

- 每天凌晨用 `node-cron` 触发
- **必须用 SQLite 的 `VACUUM INTO` 或 backup API，不能直接复制文件** —— 直接 copy 正在写入的 db 会得到损坏的副本
- 输出到 `backup/YYYY-MM-DD.db`，滚动保留最近 30 份
- **备份写完立即跑一次 `PRAGMA integrity_check`**，通过才算成功；失败则告警并保留上一份不覆盖
- 再确认 `sales` 表存在 —— 一个空但"完整"的库同样没用
- **转成单文件**：源库跑在 WAL 下，备份出来也是 WAL，那就不是"一个文件"了。
  备份完把它切到 `journal_mode = DELETE` 并清掉 `-shm` / `-wal` 边车文件。
  恢复说明写的是"把这一个 .db 复制回去"，这句承诺得是字面成立的

> 备份只验证"写出了文件"是不够的。**一个损坏的备份比没有备份更危险** —— 它让老板以为自己有后路，而真到要恢复那天才发现没有。
> 校验一个几十 MB 的 SQLite 文件是毫秒级的事，没有理由省。

### 备份状态常驻可见

顶栏常显「备份：今天 02:00」。**超过 3 天未成功备份则标红告警。** 静默失败的备份等于没有备份。

### 异地副本

本机备份防不了硬盘损坏。提供「备份到 U 盘」按钮：检测可移动盘符 → 一键复制。首次使用时引导老板准备一个 U 盘常插着。

### 恢复流程

已写成一页纸：[06-备份与恢复](06-备份与恢复.md)。三步：停服务 → 覆盖 `data/ledger.db` → 启服务。

**那页文档开头写着"请打印一份压在柜台下面"** —— 电脑开不了机的时候，你没法在电脑上看它。

## 测试策略

不追求覆盖率。**只有三类代码值得写测试，但这三类必须写。**

### 1. 移动加权成本算法（纯函数）

它是全系统错了最难发现的一段：算错不会报错，只会让毛利慢慢偏掉，而老板要到月底才察觉数字不对，那时已经无从追查。

必测用例：

| 场景 | 期望 |
|---|---|
| 正常进货加权 | `(10×50 + 10×60) / 20 = 55` |
| `old_qty = 0` 进货 | 新均价 = 进价，不是除零 |
| `old_qty < 0`（负库存时进货） | 新均价 = 进价，**不套加权公式** |
| 进完 `new_qty` 仍 ≤ 0 | 新均价 = 进价 |
| 负库存继续销售 | 均价不变，结存继续变负 |
| 整条价 550 拆成 10 包 | `unit_cost_base = 55.0000`，无精度丢失 |
| 整箱 333 拆成 6 瓶 | `unit_cost_base = 55.5000`，四位小数必要性的证据 |
| 作废进货后均价反算为负 | clamp 到 0 并产生告警，**不写入负成本** |

### 2. FIFO 核销重算（纯函数）

输入是两个有序列表，输出唯一确定，是最适合测的形状。

必测用例：

| 场景 | 期望 |
|---|---|
| 单笔收款核销多张单 | 按 `biz_date` 升序填满 |
| 收款不足 | 最后一张单部分核销，其余不动 |
| 超额收款 | 余额成为预收，不写 allocation |
| **补录一张更早的挂账单** | 重算后它排在最前，**账龄随之改变** |
| **修改某单 `biz_date` 提前** | 同上 |
| 同日多单 | 按 `(biz_date, id)` 稳定排序，重算结果可复现 |
| 作废已被核销的单 | 释放出的款项自动流向下一张未结清单 |
| 退货负单参与核销 | 抵减欠款，可能产生预收 |
| **幂等性** | 连续重算两次，结果完全一致 |

倒数第二条和"补录"两条是这套设计的立身之本，**必须有测试钉住**。

### 3. 逆向 action 的端到端不变量

作废 / 修改 / 退货每走一遍，断言三件事同时成立：

```
1. 库存结存 == 从 stock_movements 全量重算的结果
2. 客户净欠款 == SUM(未作废挂账单) − SUM(未作废收款)
3. 报表营业额 == SUM(未作废单.total_amount)
```

这三条不变量是 [02 的不变量表](02-数据模型.md#不变量)的可执行版本。它们成立，账就不会对不上。

> **不写测试的部分**：CRUD、报表查询、前端组件。它们错了看得见，改起来也便宜。

## 版本升级与数据迁移

便携包是整目录发布的，但升级**绝不能整目录覆盖** —— `data/ledger.db` 在里面。

### 升级包结构

升级包只含 `app/`、`web/`、`runtime/`，**不含 `data/` 和 `backup/`**。

`更新.bat` 的步骤：

```
1. 停服务
2. 立即做一次备份（带 integrity_check）
3. 覆盖 app/ web/ runtime/
4. 启服务 → 启动时自动执行未跑过的迁移
5. 迁移失败 → 回滚到第 2 步的备份，并提示联系维护者
```

第 2 步和第 5 步是重点：**升级是数据丢失风险最高的时刻**，比硬盘坏了概率高得多。

### 迁移纪律

- schema 变更一律新增一个 `migrations/NNN_*.sql`，**不改已发布过的迁移文件**
- SQLite 的 `ALTER TABLE` 能力有限（不能删列、不能改约束）。需要改表结构时走标准套路：建新表 → 搬数据 → 删旧表 → 改名，整个过程在一个事务里
- **迁移必须在有真实数据的库上试跑过**才能发布，空库迁移成功不说明任何问题
- 涉及数据回填的迁移（如给存量单据补 `rev = 1`）要写成幂等的，允许重复执行

### 版本号可见

顶栏角落显示版本号。远程支持时第一句话永远是"你现在是哪个版本" —— 没有这个信息，排查无从开始。
