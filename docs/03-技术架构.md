# 03 · 技术架构

## 选型决策记录

### 后端：NocoBase 作 headless 后端

一旦决定自研前端 UI，NocoBase 的"可视化搭建"这半边价值就用不上了。它在本项目中的实际定位是 **headless 后端 + 免费的运维后台**：

| 用得上 | 价值 |
|---|---|
| 数据建模 → 自动生成 REST API | 高。8 张表的 CRUD 一行不用写 |
| 后台管理界面 | **很高**。改错数据、查账、导出，自己开发至少两周 |
| 用户认证 / Token | 中 |
| 工作流引擎 | 中。二期做催收提醒有用 |
| 数据库迁移管理 | 中 |

**放弃的**：可视化搭建（它一半的价值）。这笔账认下来仍然划算，主要买的是那个开箱即用的后台。

许可证：NocoBase 2.0（2026-02 发布）已将主协议从 AGPL-3.0 调整为 Apache-2.0，并开源了一批原商业插件。本项目只用开源部分，无需商业授权。**落地前逐包核对 `package.json` 的 license 字段，不要只信博客。**

### 前端：独立 Vite 工程（方案 B）

| 方案 | 结论 |
|---|---|
| A. NocoBase mobile 插件 + 自定义区块 | ❌ 前端是 schema/formily 驱动，做极简 UI 等于逆着框架写 |
| **B. 独立前端 + NocoBase 作 API** | ✅ **采用**。UI 100% 可控，包体积小，技术栈自由 |
| C. 自研前端打包进 NocoBase 插件 | 备选。单体部署省事，但要跟它的构建体系磨合 |
| D. 放弃 NocoBase 全自研 | ❌ 后台管理界面要自己做，得不偿失 |

### 数据库：SQLite

本地单机单人，PostgreSQL 是过度配置：

- 零配置，不用单独跑数据库进程
- **整个数据库就是一个文件**，备份 = 复制文件，恢复 = 覆盖回去
- 单人读写性能绰绰有余

NocoBase 1.x 确定支持 SQLite，2.x 落地时需对实际版本核实。若 2.x 不再支持，退回单机 PostgreSQL，备份改用 `pg_dump`。

## 技术栈

**后端**
- NocoBase 2.x（Apache-2.0 部分）
- 自研插件 `plugin-ledger`：collections 定义 + 事务型业务 action
- SQLite

**前端**
- Vite + React 18 + TypeScript
- Tailwind CSS（**不用组件库**）
- TanStack Query（数据获取、缓存、失败重试）
- React Router

不用 Vant / Antd Mobile 之类组件库的原因：本项目要求字号和点击区域比常规大一号（使用者四五十岁），套组件库还得逐个覆盖样式，不如直接手写一套尺寸规范。

## API 设计

### 通用 CRUD（NocoBase 自动生成，直接用）

```
GET  /api/products:list
POST /api/products:create
POST /api/products:update
GET  /api/customers:list
GET  /api/sales:list
...
```

### 业务 action（plugin-ledger 实现）

**这是整个后端唯一需要写代码的地方。** 每个 action 在**一个数据库事务**内完成全部副作用，前端一次请求搞定一件事。

| 接口 | 事务内做的事 |
|---|---|
| `POST /api/sales:checkout` | 建销售单 → 建明细 → 读取当前 `avg_cost_base` 冻结为成本快照 → 扣 `inventory.qty_base` → 写 `stock_movements` → 现金单置 `paid_amount = total`，挂账单置 0 |
| `POST /api/purchases:receive` | 建进货单 → 建明细 → 按移动加权公式更新 `inventory.avg_cost_base` 和 `qty_base` → 写 `stock_movements` |
| `POST /api/payments:collect` | 建收款记录 → 按 `biz_date` 升序 FIFO 核销该客户未结清销售单 → 写 `payment_allocations` |
| `GET /api/reports:dashboard` | 今日营业额、今日毛利、本月毛利、欠款汇总、异常提醒 |
| `GET /api/reports:profit` | 日/月毛利趋势、单品利润排行、滞销预警 |
| `GET /api/customers:debts` | 欠款客户列表，含总欠款与账龄，按账龄倒序 |
| `POST /api/backup:now` | 立即备份数据库文件 |
| `GET /api/seed:brands` | 列出预置目录中的品牌，供首次启用时勾选 |
| `POST /api/seed:import` | 按勾选的品牌导入商品骨架，价格留空。**跳过已存在的同名商品**，可重复调用 |

### 为什么业务逻辑不能放前端

若前端直接调通用 CRUD 来"卖一笔货"，需连发四个请求：建单 → 建明细 → 扣库存 → 写流水。中间任何一步失败，数据就脏了且无法自愈。必须服务端事务包裹。

## 部署：Windows 免安装便携包

柜台电脑是 Windows 家用机，老板自己用。**不上 Docker**（太重、要 WSL2、吃内存）。

### 发布物结构

```
烟酒台账/
├─ 安装.bat            首次运行一次：注册服务 + 建桌面图标
├─ 卸载.bat
├─ runtime/node/       便携版 Node.js，免安装
├─ app/                NocoBase + plugin-ledger
├─ web/                前端静态文件
├─ data/
│  └─ ledger.db        ← 全部数据就这一个文件
├─ backup/             自动备份
└─ tools/nssm.exe      Windows 服务管理器
```

整个目录可整体复制。**换电脑、重装系统只需拷贝这个文件夹。**

### 后台运行

用 [nssm](https://nssm.cc/) 把 Node 服务注册为 Windows 服务：

- 无黑窗口（老板不会误关）
- 开机自启
- 崩溃自动重启

### 桌面入口

创建快捷方式，目标为：

```
msedge.exe --app=http://localhost:13000
```

`--app` 模式无地址栏、无标签页、独立任务栏图标，看起来就是个本地桌面软件，而不是"打开浏览器输网址"。Edge 在 Win10/11 上必定存在，不需要假设装了 Chrome。

端口选 `13000` 一类不常用端口，避开冲突。仅监听 `127.0.0.1`，不对外暴露。

### 前后端同域

前端静态文件由 NocoBase 服务一并托管：`/` 出前端，`/api` 走后端。省掉 CORS 和 cookie 跨域问题。

## 备份与恢复

> **本地部署的头号风险不是技术问题，是数据丢失。**
> 跑在云上硬盘坏了还有服务商快照；跑在柜台电脑上，硬盘坏了就是几年台账全没，而老板绝不会自己备份。
> 因此备份不是运维事项，是**一期必须交付的产品功能**，优先级高于利润报表。

### 自动备份

- 每天凌晨用 `node-cron` 触发
- **必须用 SQLite 的 `VACUUM INTO` 或 backup API，不能直接复制文件** —— 直接 copy 正在写入的 db 会得到损坏的副本
- 输出到 `backup/YYYY-MM-DD.db`，滚动保留最近 30 份

### 备份状态常驻可见

顶栏常显「备份：今天 02:00」。**超过 3 天未成功备份则标红告警。** 静默失败的备份等于没有备份。

### 异地副本

本机备份防不了硬盘损坏。提供「备份到 U 盘」按钮：检测可移动盘符 → 一键复制。首次使用时引导老板准备一个 U 盘常插着。

### 恢复流程

写成一页纸图文说明放进 `docs/`，步骤控制在三步以内：停服务 → 覆盖 `data/ledger.db` → 启服务。
