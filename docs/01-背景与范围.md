# 01 · 背景与范围

## 业务背景

烟酒店的进销存有两条差异很大的货品线：

**香烟**
- 烟草公司专卖，网上订货，有订单号、送货单、配额
- 进价基本固定，不存在比价采购
- 单位是**条 / 包**（1 条 = 10 包）
- 拆条卖包是常态，且**整条价与拆包价不成比例**（一条 550，单包 57 而非 55）

**酒水及其他**
- 多供应商、多品牌，有议价空间
- 有厂家返点、赠品
- 单位是**箱 / 瓶**（1 箱 = 6 或 12 瓶）

销售端有三种形态：

1. **零散零售** —— 笔数最多，单笔金额小
2. **团购 / 宴席大单** —— 整箱走货，常带折扣
3. **赊账挂账** —— 熟客、单位客户、年底结算。这是烟酒店最大的资金痛点

## 目标用户

**单店老板一人使用**。推论：

- 不需要角色权限体系，不需要操作留痕对账，不需要交接班
- 不需要"店员看不到进价"这类数据隔离
- 使用者可能是四五十岁，**界面字号和点击区域要比常规大一号**

## 使用场景

柜台电脑常开，卖一笔录一笔。偶尔忙不过来会攒几笔回头补录，因此**所有单据的业务日期必须可改**。

## 一期范围

### 做

- **商品管理** —— 名称、拼音、分类、规格、双单位、双价格、建议售价
- **进货** —— 录进货单，自动加库存、更新加权成本
- **卖货** —— 录销售单，自动扣库存、冻结成本快照、计算毛利
- **赊账与催收** —— 挂账销售、客户欠款总账、账龄、收款核销
- **利润报表** —— 日 / 月毛利、单品利润排行、滞销预警
- **看板** —— 今日营业额、今日毛利、欠款提醒、异常提醒

### 明确不做

| 不做 | 理由 |
|---|---|
| 盘点对账 | 一期先让流水跑通。`stock_movements` 表已预留，二期只是多一种 movement 类型 |
| 条码扫码 | 纯 PC + 键盘流已经足够快，且需要先建条码库 |
| 移动端 | 柜台电脑覆盖主要场景 |
| 多门店 / 多租户 | 自用，单实例部署 |
| 多角色权限 | 单人使用 |
| 批次 / 序列号 | 移动加权成本已满足利润核算需求 |
| 小票打印 | 台账系统，不是收银系统 |

## 关键设计红线

以下几条是踩过的坑，实现时不得违反：

**1. 库存允许为负，不做硬拦截**

老板忘记录进货是常态。若系统卡着"库存不足不让卖"，他会当场弃用。正确做法是照常记录，库存为负时在列表标红提示"可能漏记进货"。**软提醒，不拦路。**

**2. 业务日期与记录时间必须分离**

每张单据都有 `biz_date`（业务发生日，可改）和 `created_at`（系统时间，不可改）。**所有报表按 `biz_date` 统计**。若用 `created_at` 当业务时间，补录一笔上周的账会静默算错上周报表。

**3. 成本在成交那一刻快照冻结**

移动加权成本随每次进货变动。历史单据的成本必须是不可变事实，不能每次报表都重算——否则上个月的利润会随这个月进货而变，老板会认为软件在骗他。

**4. 结账不弹对话框**

九成单子是现金。卖货页只给两个按钮：「现金收讫」直接完成，「挂账」才需要选客户。绝大多数进销存软件死在"非要你选支付方式、填备注、确认两次"。

**5. 毛利不是净利**

界面上必须明写"毛利"二字，并注明不含房租水电人工。否则老板会拿它当净利，然后认为软件算错了。

## 验收标准

功能清单不是验收标准，**操作耗时才是**：

| 场景 | 目标 |
|---|---|
| 卖一条中华（现金） | ≤ 3 秒，全程键盘，不碰鼠标 |
| 卖三样商品并挂账 | ≤ 15 秒 |
| 查"谁欠我钱" | 打开即见，0 次点击 |
| 查本月毛利 | ≤ 2 次点击 |
| 补录昨天一笔漏单 | ≤ 10 秒 |

如果卖一笔货需要划三屏、打五个字，功能做得再全，老板用两天就会回去用本子。

## 启用门槛：初始商品库

这是这类软件**最容易死掉的地方**，比任何功能缺失都致命。一个烟酒店几百个 SKU，如果要求老板上线前先把商品库建全，他大概率录到第 50 个就放弃了。

两条路同时铺，缺一不可：

### 1. 预置商品目录，按品牌勾选导入

软件内置一份常见烟酒的**商品骨架目录**（见 `seed/products.sample.json`），首次启用时让老板勾选「你店里卖哪些牌子」，一键导入。

**目录只含骨架，不含价格：**

| 字段 | 来源 | 理由 |
|---|---|---|
| 名称、品牌、规格、拼音、单位换算 | 预置 | 公开知识，卷烟一律 1 条 = 10 包 |
| 进价 | **必须老板填** | 各店不同，外部无从知道 |
| 售价 | **必须老板填** | 烟草零售价各省不同且常调，酒水价格波动大 |

建库最烦的是打字，预置目录把打字全干掉，老板只剩填两列数字，可做成表格批量填。

**关键约束：绝不可全量导入。** 500 个 SKU 一股脑塞进去，搜 `zh` 会跳出一堆他根本不卖的牌子，搜索体验直接被污染。必须按品牌勾选，勾 15 个品牌导入 60 个 SKU 刚好够用，其余留在库里以后再导。

**预置目录不是权威数据**，会有错漏（规格记混、已停产、新品缺失）。导入后必须可编辑可删除，箱规尤其要提示按实际到货确认——白酒箱规 6/12/4 瓶各地差异大。

> 更权威的来源：老板的烟草订货系统里就有他能订的全部卷烟规格清单，比任何预置目录都准。若能导出或截图，优先用那个。

### 2. 卖货时即时新建商品

预置目录再全也覆盖不了本地小众货。**搜索无结果时，当场就能建：**

```
搜索「泸小二」→ 无结果
  ↓ 回车
就地弹出三个字段：名称 / 进价 / 售价
  ↓ 填完回车
商品建好，同时加入当前这笔单，继续结账
```

拼音自动生成，单位默认「瓶」，规格留空。**全程不离开卖货页，不打断这笔生意。**

商品库在日常使用中自然长出来，这比任何导入方案都重要——因为它让"商品库不全"不再是阻塞问题。

### 为什么不在产品里接在线 AI

这个需求看起来是"接入 AI 生成商品库"，本质却是**"要一份现成的目录"**，而目录是静态数据，生成一次就固定了。

服务跑在柜台电脑上，可能没有稳定网络。为静态数据引入 API key、联网依赖、超时处理和调用成本，是净亏损。**目录在开发期生成好，随软件打包发布即可。**

二期若要用 AI，更值钱的方向是**读取老板自己的数据**——烟草订货单截图 OCR 成进货单、现有 Excel/纸质台账批量导入。这类场景 AI 不需要"知道"什么，只需要"读取"，准确率高得多。
