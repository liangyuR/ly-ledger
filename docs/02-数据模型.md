# 02 · 数据模型

## 设计原则

**1. 库存流水是唯一真相来源**

所有库存变动（进货、销售、退货、损耗、未来的盘点差异）都写入只追加的 `stock_movements`。`inventory` 表只是这张流水的物化快照，任何时候都能从流水重算出来。

这条是为了可回溯性。小店软件最后翻车基本都翻在"账对不上又查不出原因"。

**2. 成本快照不可变**

`sale_items.unit_cost_base_e4` 记录成交那一刻的加权成本，`sales.cost_amount_cents` / `gross_profit_cents` 同理。历史单据的成本是既成事实，不是计算结果。

**3. 业务日期与记录时间分离**

`biz_date`（可改）用于所有报表统计，`created_at`（不可改）仅用于审计追溯。

**4. 允许负库存**

不做写入拦截，仅在展示层标红提醒。

**5. 单据不可变，核销可重算**

已提交单据不原地修改，改错走「作废 + 重建」。`payment_allocations` 是可从 `sales` + `payments` 完整重算的**派生表**，不是历史流水。

详见 [05-变更与撤销](05-变更与撤销.md)，这条是整个逆向流程的地基。

## 单位约定

**金额和数量一律用整数存，不用浮点。** 字段名的后缀就是单位，改后缀等于改语义：

| 后缀 | 单位 | 换算 | 用在 |
|---|---|---|---|
| `_cents` | 分 | 1 元 = 100 | 所有金额 |
| `_e4` | 万分之一元 | 1 元 = 10000 | 单位成本 |
| `_milli` | 千分之一 | 1 包 = 1000 | 所有数量 |

单位成本用 1e-4 而不是 1e-2，是因为整条进价 550 拆 10 包 = 55.0000，而整箱 333 拆 6 瓶 = 55.5000 —— 两位小数会累积误差。

> **为什么不用 DECIMAL**：SQLite 没有这个类型。声明 `decimal(12,2)` 只会落成 NUMERIC 亲和性、底层用 REAL（双精度浮点）存储。
>
> 台账系统里"金额是浮点"是不可接受的：它不会当场报错，只会让某天的账差一分钱，然后你查三个小时。用整数则这一整类问题根本不存在 —— **不需要舍入纪律，因为没有可舍入的东西**。
>
> 代价是读写时要换算。换算集中在一处，比在每个计算点上守纪律可靠得多。

## 表结构

### products 商品

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| name | string | 商品名，如「中华(硬)」 |
| pinyin_full | string | 全拼，如 `zhonghuaying` |
| pinyin_abbr | string | 首字母，如 `zhy` |
| category | enum | `cigarette` / `liquor` / `other` |
| brand | string | 品牌 |
| spec | string | 规格描述，如「20支×10包」 |
| base_unit | string | 基础单位：包 / 瓶。**库存与成本一律以此计量** |
| pack_unit | string | 包装单位：条 / 箱。可空 |
| pack_ratio | int | 1 包装单位 = N 基础单位，默认 1 |
| price_base_cents | INTEGER | 按基础单位的售价（单包价） |
| price_pack_cents | INTEGER | 按包装单位的售价（整条价）。**独立定价，不是 price_base_cents × pack_ratio** |
| barcode | string | 条码，一期不用，预留 |
| is_active | bool | 是否在售 |
| sort_weight | int | 手动置顶权重，默认 0 |

**一个商品只有一条记录，不按单位拆分。**

「中华(硬) 整条卖」和「中华(硬) 单包卖」是同一个商品的两种卖法 —— `base_unit=包`、`pack_unit=条`、`pack_ratio=10`，两个价格分别记在 `price_base_cents` 和 `price_pack_cents`。

绝不可建成两条商品记录。否则**库存会裂成两份**：卖一条扣的是 A 的库存，卖一包扣的是 B 的库存，两边互不知情。进 10 条之后卖 3 包，账当场就错，而且错得极隐蔽 —— 报表上两个"中华(硬)"各有各的结存，谁也看不出哪个是对的。

因此商品唯一性按 `name` 判定：批量导入时同名一律跳过，不新建。

两个拼音字段在录入商品时按名称自动生成，允许手工修正（多音字）。搜索时三路匹配：

```sql
name LIKE '%q%' OR pinyin_full LIKE 'q%' OR pinyin_abbr LIKE 'q%'
```

**两个都要**：只做首字母会逼老板记缩写，只做全拼则打字太多。这样 `mt` 和 `maotai` 都能命中「茅台飞天」。

### payment_allocations 核销明细

FIFO 自动核销的结果，用于计算账龄和"某张单还欠多少"。

> **这是派生表，不是流水。** 它可以被整体删除并从 `sales` + `payments` 完整重算，结果唯一确定。
> 任何影响输入的操作（作废、修改、补录、改 `biz_date`、退货）之后，**必须对相关客户全量重跑核销**。
> 重算算法与触发时机见 [05-变更与撤销](05-变更与撤销.md)。

## 移动加权平均成本算法

### 进货时

```
new_qty = old_qty + in_qty

if new_qty <= 0:
    new_avg = in_cost        # 进完仍为负或归零，历史成本无参考意义
elif old_qty <= 0:
    new_avg = in_cost        # 进货前是负库存或零库存，旧均价无效
else:
    new_avg = (old_qty * old_avg + in_qty * in_cost) / new_qty
```

**必须显式处理 `old_qty <= 0` 的分支**。因为允许负库存，标准加权公式在这里会算出负成本或除零。

### 销售时

```
avg_cost 不变
qty_base_milli -= sale_qty_base      # 允许变负
```

库存变负后继续销售，仍沿用最后已知的 `avg_cost_base_e4` 估算毛利。这是有偏差的，但比拒绝记账好——下次进货时成本会自动校正回来。

### 精度

加权平均必然除不尽（`(10×520 + 5×533) / 15`），这是整数方案唯一需要动脑的地方：

- 计算时用 `BigInt` 或先乘后除，**不要先除后乘**
- 结果按 `_e4` 精度**四舍五入到整数**再落库
- 由此产生的误差上限是 0.0001 元/单位，在库存量级下可以忽略；且下次进货时会被新的加权覆盖，不会累积

**永远不要把 `_e4` 换回浮点再算。** 换算只发生在两个地方：入库前（元 → 整数）和出参时（整数 → 显示用字符串）。中间一律整数。

## 欠款与核销规则

### 账务模型

赊账不是独立模块，而是销售单的结算属性：

```
某张单已核销额 = SUM(payment_allocations.amount WHERE sale_id = 该单)
某张单未结清额 = sales.total_amount_cents − 已核销额

客户净欠款     = SUM(该客户未作废挂账单.total_amount_cents)
               − SUM(该客户未作废收款.amount)

客户账龄       = 今天 − 最早一张未结清单的 biz_date
```

**所有口径一律过滤 `voided_at IS NULL`。**

客户净欠款为负时即为**预收**，界面显示「预收 ¥300」，不进催收队列。账龄只对净欠款为正的客户有意义。

### FIFO 自动核销

老板的心智是"老王还了 500"，不关心具体是哪几笔。所以收款记在**客户**身上，系统自动核销：

```
1. 取该客户所有未作废挂账单，按 (biz_date, id) 升序
2. 依次核销，每核销一张写一条 payment_allocations
3. 收款金额用完即止
4. 若核销完所有单仍有剩余 → 余额成为**预收**，不写 allocation，
   下次挂账买货时自动抵扣
```

> **注意这不是"来一笔收款追加核销一笔"的增量过程。**
> 实际实现是：删除该客户全部 allocations → 按上述规则整体重算。
> 因为补录、改期、作废都会改变 FIFO 顺序，增量追加必然算错账龄。详见 [05-变更与撤销](05-变更与撤销.md)。

界面默认只显示「老王共欠 ¥3,200，最早一笔 45 天前」。按单核销明细收在详情页里，需要时才看。

## 不变量

这些约束不写进代码就会在某个角落被违反，且违反时**不会报错，只会算错**。建表时能加 CHECK 的加 CHECK，加不了的在 action 入口校验。

| # | 不变量 | 违反后果 |
|---|---|---|
| 1 | `customer_id IS NOT NULL` ⟺ `settle_type = 'credit'` | 现金单被算进欠款，或挂账单收不回来 |
| 2 | 报表、看板、库存汇总一律过滤 `voided_at IS NULL` | 作废单重复计入营业额 |
| 3 | `total_amount_cents = original_amount_cents − discount_amount_cents` | 抹零金额凭空消失或重复扣减 |
| 4 | `qty_base_milli = qty × pack_ratio`（unit 为 pack 时），否则 `= qty` | 库存单位串味，条和包混算 |
| 5 | `cost_amount_cents = qty_base_milli × unit_cost_base_e4`（按 4 位舍入） | 毛利对不上 |
| 6 | `stock_movements` 只 INSERT，永不 UPDATE / DELETE | 失去唯一真相来源，账查不回去 |
| 7 | 一张单的 `sale_items` 全部落在同一事务内，无半成品单 | 出现有单无明细的幽灵记录 |
| 8 | 退货单 `total_amount_cents < 0`，作废单 `voided_at` 非空，二者不重叠 | 退货被当成作废，历史营业额缩水 |

第 1 条最容易被"常识"带偏：将来一旦有人想支持"熟客付现金也记客户"，它就会被悄悄打破，而欠款列表会在那一刻开始撒谎。**要支持这个场景，正确做法是新增 `settle_type` 值并同步修订欠款口径，不是放松这条不变量。**
